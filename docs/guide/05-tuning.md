# 05 · 飞行调参

调参从观察现象开始。先把机械、传感器和供电恢复到一致状态，再动控制参数；每次只改一个值，完成同样的短飞行后比较。这样两三次飞行就能知道变化来自哪里。

## 5.1 先判断是不是参数问题

下面这些现象应先回到硬件：

| 现象 | 先检查 |
| --- | --- |
| 起飞瞬间向一侧翻倒 | M0–M3 位置、转向、CW/CCW 桨、IMU 朝向 |
| 某一侧始终无力 | 桨叶损伤、电机弯轴、接头、电机温度与电池压降 |
| 高频细碎振动 | 桨叶变形、电机轴、橡胶圈、电机高度、IMU 固定 |
| 定点只在某种地面失效 | 地面纹理、反光、光照、光流窗口 |
| 高度值跳变 | ToF 窗口、模块倾斜、近距离盲区和线束 |
| 换电以后重心变化 | 电池位置、附件位置和实际起飞重量 |

机械状态稳定后，用同一块电池、同一处地面和同一高度做对比。首选的测试动作是“0.65 m 起飞 → 回中悬停 5 秒 → 降落”。

## 5.2 认识四层控制

Open32Drone 的控制器由内到外依次工作：

```text
角速度环 → 姿态角环 → 高度/速度环 → 水平位置环
```

内环必须先稳定，外环才能调好。P 决定纠正有多积极；I 用来消除持续偏差；D 抑制变化过快造成的过冲。调参时通常先看 P，再看 I，最后只在确有需要时调整 D。

查看所有参数：

```text
p
```

查看或写入单个参数：

```text
p CTL_R_P
p CTL_R_P 4.02
```

写入会保存到 NVS。改之前记录旧值，改完等待一秒再读取确认。

## 5.3 姿态抖动与回正

标准姿态参数如下：

| 功能 | Roll | Pitch | 默认值 |
| --- | --- | --- | ---: |
| 角度 P | `CTL_R_P` | `CTL_P_P` | 4.47 |
| 角速度 P | `CTL_R_RATE_P` | `CTL_P_RATE_P` | 0.05 |
| 角速度 I | `CTL_R_RATE_I` | `CTL_P_RATE_I` | 0.20 |
| 角速度 D | `CTL_R_RATE_D` | `CTL_P_RATE_D` | 0.001 |

### 高频抖动

如果飞机能起飞，但机身快速、连续地抖动，先修复桨和电机振动。机械正常后，将对应轴的角速度 P 降低 5–10%。例如 Roll 从 `0.050` 改为 `0.045`：

```text
p CTL_R_RATE_P 0.045
```

重新做同样的 5 秒悬停。抖动减轻且控制仍有力度，再在 Pitch 轴按同样幅度处理；不要一次同时改 P、I、D。

### 慢速来回摆动或回正过猛

低频、大幅度摆动更可能来自外层角度 P。把 `CTL_R_P` 或 `CTL_P_P` 降低约 10%，例如 `4.47 → 4.02`。如果飞机显得反应迟钝、松杆后很久才回平，可向原值方向小幅增加。

### 持续偏向一侧

固定方向的倾斜通常由重心、弱电机、机架变形或加速度计偏置造成。先移动电池让重心回到中央，再重新运行 `ca`。只有机械与校准一致、偏差仍可重复时，才分析 I 项。

## 5.4 高度问题

高度控制的主要参数是：

| 参数 | 默认值 | 作用 |
| --- | ---: | --- |
| `ALT_P` | 0.747 | 高度误差的主要纠正力度 |
| `ALT_I` | 0.10 | 消除长期高度偏差 |
| `ALT_D` | 0.20 | 根据垂直速度抑制过冲 |
| `ALT_HOVER` | 0.49 | 标称悬停推力前馈 |
| `ALT_VEL_MAX` | 0.45 | 最大升降速度 |

飞机围绕目标高度缓慢上下摆动时，先确认 ToF 数据连续，再把 `ALT_P` 降低约 10%，例如：

```text
p ALT_P 0.67
```

起飞后稳定，但高度长期慢慢偏低或偏高，可以小幅检查 `ALT_I`。接近目标时明显冲过头再反向，则重点观察 ToF 速度和 `ALT_D`。

`ALT_HOVER` 表示标准电压附近维持高度所需的集体推力。81 g、60 mm 桨的参考值是 0.49。飞机在传感器正常、姿态平稳的情况下长期靠较大高度修正支撑，可从飞行日志估计悬停电机均值，再以很小幅度调整。不要用提高 `ALT_HOVER` 掩盖电池老化或弱电机。

## 5.5 水平漂移与定点

定点控制依赖光流，默认参数为：

| 参数 | 默认值 | 作用 |
| --- | ---: | --- |
| `POS_HOLD_P` | 0.85 | 位置误差转换为目标速度 |
| `POS_VEL_P_X/Y` | 0.35 | 水平速度 P |
| `POS_VEL_I_X/Y` | 0.04 | 水平速度 I |
| `POS_STICK_V` | 0.70 | 摇杆最大水平速度 |

先在清晰纹理地面上运行 `flow`，确认数据新鲜。原地偏航时若位置出现圆周漂移，检查模块是否位于标准前移 24 mm 位置、安装平面是否水平。持续向固定方向漂移时重新检查光流零偏、电池重心和 IMU 校准。

飞机慢慢离开目标而不积极回来，可以小幅增加 `POS_HOLD_P`；围绕目标左右来回摆，则小幅降低。一次改 5–10%，每次使用相同的定点高度和飞行时间。

## 5.6 电池与动力变化

参考电池满电约 4.2 V，放电过程中电机可用推力会下降。主板通过 `GPIO1/A0` 读取 100 kΩ / 100 kΩ 分压后的电压，辅助定高和定点使用有界前馈补偿。

先用 `pw` 和万用表把 `PWR_VOLT_SCALE` 校准准确。新电池和低电量电池各做一次同样的 5 秒悬停，比较日志里的 `voltage`、`hoverFF`、`voltComp` 和四路电机输出。如果电压下降时四路同时接近饱和，优先检查电池内阻、桨叶和电机，而不是继续提高 PID。

## 5.7 用日志比较两次飞行

飞机上锁后运行：

```text
log dump
```

保存 CSV 后，可用仓库中的分析脚本快速检查：

```bash
python3 software/simulation/course/analyze_log.py \
  --csv /path/to/flight.csv \
  --output output/my-flight-analysis
```

至少比较以下曲线或字段：

- 姿态目标与实际 Roll/Pitch；
- ToF 高度与高度目标；
- 光流速度与位置误差；
- 四路电机输出及其是否饱和；
- 电池电压和补偿量；
- 问题发生前后的时间点。

一次有效调参记录只需要四项：原参数、修改值、相同飞行动作、观察结果。变好就保留并继续小幅调整；变差就恢复旧值。这样很快能形成适合这台飞机的参数表。

当飞机能重复完成定点起飞、5–10 秒悬停、小范围平移和自动降落，就可以把控制权交给 ROS。

## 5.8 按错误提示排查

## 启动与预检失败

### 没有串口输出，或 LED 只闪一下

1. 确认在 `0x0` 写入的是完整 merged 镜像，而不是只用于 OTA 的 app 镜像；
2. 使用正确的 ESP32-S3 USB 端口和 115200 波特率；
3. 完整擦除后再通过 USB 刷写一次；
4. 查看启动日志中的分区、反复复位或欠压信息。

### 初始化完成后 GPIO21 一直闪烁

执行 `pw`，并用万用表核对。滤波电压不高于 `3.10 V` 并持续 `1.5 s` 后进入 `2 Hz`
闪烁；只有电压不低于 `3.20 V` 并持续 `1.0 s` 才退出。闪灯只做提示，不会自动降落或
上锁。不带分压电路的旧板应设置 `PWR_VOLT_PIN=-1`，不能让悬空 ADC 保持启用。

### `motor PWM unavailable`

说明四路 LEDC 电机通道没有全部 attach 成功，不能绕过预检。确认固件使用固定版本的
Arduino-ESP32 core 构建；相机或其他模块没有占用相同 LEDC 资源；电机引脚按左后、
右后、右前、左前对应 `4, 3, 6, 5`。

### `gyro calibration incomplete`

把飞机放在刚性水平面上冷启动，至少两秒不要触碰。仍不能完成时，用 `imu` 查看失败
原因和标准差，排除振动、气流、桌面晃动和损坏电机。`cg` 只重新开始陀螺校准，不能
代替 `ca`。

### `invalid RC calibration/mapping`

给接收机供电，运行 `cr` 并完成八步提示。每个控制量必须映射到互不重复、可持久化的
`0..7` 通道。使用 Android 或 ROS 时不要求接收机开机。

### 参数存储错误

如果 `sys` 显示 `Parameter storage: ERROR`，固件会拒绝解锁。不能带着无法保存的校准
继续飞。完整擦除、重刷并重新执行 `ca`/`cr`；若再次出现，应排查 Flash/NVS 硬件和
分区。

### 循环频率低或不稳定

不能因为一个 `rate` 数字就删除安全检查或关闭飞行日志；正常结果应接近固定 300 Hz。
上锁后执行 `perf reset`，保持一种负载运行 10-20 秒，再保存 `time` 和 `perf`。飞机单独、
Android、ROS、QGC 参数页要分别测试。比较截止时间错过次数、最大迟到量、p95/p99/最大
时延和各命名阶段耗时。`imu acquire` 是选定后端执行 `read()` 的成本；不同传感器系列的
驱动内部可能还有自己的传输。固定节拍的主动等待有意不计入 `perf`，因此抽样总耗时是
实际执行成本，不是完整 3.33 ms 周期。CLI、MAVLink 或后台阶段最大值很大时才指向对应
路径。25 Hz 日志是 RAM 环形缓冲，必须先证明后台维护阶段耗时异常，才能归因给日志。

## TF-0850 与校准

### 飞机放在地面，Android 提示 ToF 未就绪

TF-0850 约 `20 mm` 以下属于盲区。新鲜的盲区数据包仍是有效地面准备证据，只是没有
可显示的数值距离。Android 提示是诊断信息，不是额外起飞否决。按钮不可用时应排查
MAVLink 连接或物理 SBUS 控制权。

执行 `flow`，确认：

- `TOF UART healthy: 1`；
- 数据年龄小于 `150 ms`；
- 有数值距离或 `blind-zone: 1`；
- 数据包计数持续增加。

### 加速度计校准被拒绝

拆桨、上锁状态运行 `ca`，按提示依次放置六个面，并在采样期间保持静止。校准是事务
式的：任一面无效、噪声过大、重力模长、比例或残差不合格，整组候选都会被拒绝，
之前参数继续生效。

### 相同套件装出的飞机表现不同

标准机架应共用同一套默认控制参数。单机差异应先靠机械一致性和 `ca`/`cr` 解决，
不能靠隐藏 Trim：

- 电机/桨叶型号与方向；
- 弯轴、松动机臂或电机高度不一致；
- IMU 刚性固定并与推力平面平行；
- 电池位置与重心；
- 向下模块方向和标准 `24 mm` 前向偏置；
- 校准平面与振动。

当前没有自动配置迁移或悬停 Trim 学习去偷偷覆盖复制的控制参数。

## Android 链路与控制

### `ENETUNREACH (Network is unreachable)`

手机没有到所配置飞机地址的 Wi-Fi 路由，或 Android 重建了该路由。直连 AP 模式下，
手机连接飞机 SSID，地址保持 `192.168.4.1`；路由器 STA 模式下，手机连接同一路由器，
并把固件 `wifi` 命令打印的 DHCP 地址填入 **工具 > 飞机地址**。关闭 VPN、授予局域网
权限，并用浏览器访问：

```text
http://<飞机地址>:8080/api/ota/status
```

客户端会把 MAVLink、图传和 OTA 绑定到能够到达所配置地址的 Android Wi-Fi 网络；
旧 socket 失效后会关闭，并在该路由恢复后重连，不会退回蜂窝网络。

### 按钮全部是灰色

查看顶部状态：

- 未连接：没有 MAVLink 心跳；
- 物理 SBUS 优先：松开摇杆等待控制权空闲；若只用 Android，也可关闭接收机；
- App 进入后台：回到前台，进入后台会有意停止手动控制流。

Android 控制不需要先打开物理遥控器。

### 起飞后约几秒自动降落

常见原因是手机停止发送新鲜控制流、Wi-Fi 路由变化，或旧客户端在起飞后发送了陈旧的
零油门帧。使用匹配的 APK/固件，让 App 保持前台，并检查状态文本中的 `link loss`。
不能靠增大失联时间掩盖坏链路。

## ROS 2 连接与命令

### 有话题名字但没有数据

节点可以在飞控未连接前创建话题。检查：

```bash
ping -c 3 <飞机地址>
ros2 run open32drone_driver control status
ros2 topic echo /open32drone/connected --once
```

飞机直连 AP 使用 `192.168.4.1`；STA 模式启动 ROS 时传入同一 DHCP 地址：
`aircraft_ip:=<飞机地址>`。

关闭控制这架飞机的 Android 和其他客户端，并确认所选 `local_udp_port` 没有被其他
MAVROS 进程占用。`connected: false` 的旧
`/open32drone/UAS1/state` 样本不代表连接成功。

### `rqt` 报 QoS 不兼容

订阅 Reliable 公共桥接话题 `/open32drone/imu/data`、`/open32drone/odom`、
`/open32drone/pose`、`/open32drone/range/downward`，不要直接用 MAVROS
sensor-data 话题。仍有告警时，确认启动的是完整
`open32drone.launch.py`，且 `interface_bridge` 正在运行。

### `/open32drone/cmd_vel` 没反应

飞机必须已连接、解锁、位姿新鲜并进入 Offboard ACTIVE。先使用 `control velocity`，
并查看：

```bash
ros2 topic echo /open32drone/offboard/status
ros2 topic echo /open32drone/flight/status
```

直接 `/open32drone/cmd_vel` 必须连续发送；物理 SBUS 动作优先。不能通过改固件增益来补偿尚未
激活的 Offboard。

## OTA 失败

只有飞机已上锁、已落地、电机停止、自动飞行和 Offboard 均未激活，并且当前镜像已
通过启动验证时才接受 OTA。只能上传 app 镜像，不能上传 USB merged 镜像。查看：

```text
http://<飞机地址>:8080/api/ota/status
```

始终保留 USB 恢复条件。传输失败应保留当前运行分区；新镜像启动验证失败应自动回滚。
