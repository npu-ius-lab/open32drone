# 07 · Simulation and reinforcement learning

The ROS chapter introduces state, targets and actions. Reinforcement learning
uses the same feedback idea in a numerical environment. Here, a geometric PD
controller allocates attitude and thrust while a PPO policy adds a three-axis
acceleration correction. The examples do not replace the firmware controller.

## Start with the numerical hover exercise

From the repository root:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install --upgrade pip
python3 -m pip install numpy torch matplotlib
python3 software/simulation/course/hover_lab.py \
  --output output/my-first-hover \
  --iterations 400 --envs 128 --device cpu
```

The output contains `training.csv`, `policy_initial.pt`, `policy_final.pt`,
TorchScript `actor.pt`, `evaluation.json` and `config.json`. Compare PD and PPO
on held-out disturbances, not only the training reward. A learned policy need
not outperform a well-tuned PD controller in a calm environment.

## Understand the model

The example uses an 81 g aircraft. Average hover force is approximately
`0.081 × 9.80665 / 4 = 0.1986 N` per motor. A 50,000 rpm unloaded motor rating
does not specify loaded thrust. The coarse model uses approximately 0.419 N
maximum force per motor and a 40 ms response initial estimate; these are
learning-model assumptions, not values to copy into flight calibration.

The 35-dimensional observation combines position/velocity errors, attitude,
angular rates, reference motion, previous action, error integration, estimated
motor forces and voltage. The three policy actions are residual accelerations
bounded to ±4 m/s². Randomized mass, inertia, thrust and disturbances discourage
overfitting to one idealized aircraft.

## Optional Isaac visualization

Prepare a compatible USD asset first, then use Isaac's own Python environment:

```bash
/path/to/isaac-sim/python.sh \
  /path/to/open32drone/software/simulation/rl_demo/native_isaac.py \
  --package /path/to/compatible-asset \
  --run /path/to/open32drone/output/rl-demo/my-run \
  --output /path/to/open32drone/output/rl-demo/my-run/native \
  --seconds 34 --record --visible
```

The adapter applies forces and moments every 5 ms; PhysX integrates motion.
It does not drag the aircraft along the target path. Before real-aircraft
experiments, replace estimated motor curves with measurements, model sensor
noise/delay/dropouts, and validate policy inputs through recorded-data replay.
No command here deploys a policy to the real aircraft.


## What is available

The [hardware directory](../../software/hardware/README.md) supplies frame 3MF/STEP files.
The [simulation directory](../../software/simulation/README.md) supplies numerical dynamics,
control exercises, PPO training/evaluation and an optional Isaac adapter.

A complete aircraft URDF/USD scene, Gazebo flight plugin and trained weights
are **not included**. Do not interpret tutorial videos as installable assets.
The ROS package controls a physical aircraft; it is not a simulator backend.

## Preparing an asset

Use metres, kilograms and seconds. Adopt ROS FLU for the body frame (X forward,
Y left, Z up); explicitly transform to the firmware's body convention where
needed. Do not copy CAD coordinates directly into flight parameters.

A useful hierarchy is:

```text
base_link
├── rotor_0_link  (rear left)
├── rotor_1_link  (rear right)
├── rotor_2_link  (front right)
├── rotor_3_link  (front left)
├── battery_link (fixed)
├── camera_link  (optional, fixed)
├── imu_link     (fixed sensor frame)
└── flow_tof_link (fixed sensor frame)
```

Keep geometry scale, centre of mass and inertia separate. Measure the assembled
aircraft; a frame model does not include all PCB, wiring, motor and battery mass.
Use simple collision geometry and avoid overlapping collision bodies. Confirm
rotor direction from the actual motor/propeller arrangement.

The numerical example uses 0.081 kg and 60 mm propellers with approximate
inertia and thrust. These are teaching model values, not automatic calibration
of another airframe. See `software/simulation/rl_demo/model.json`.

## Optional Isaac adapter

`native_isaac.py --package <asset-root>` currently expects
`<asset-root>/USD/open32droe/robot.usd` and all referenced meshes/materials.
The path spelling is the adapter's existing contract. Supply a compatible
asset before using this optional script; no private asset path is required or
provided by this repository. Inspect the adapter before adapting a different
scene. Physics/renderer compatibility depends on the installed Isaac version.

Numerical PPO exercises do not need that scene. Start with
`software/simulation/course/hover_lab.py`, then train/evaluate the trajectory example.

## Validation sequence

Check scale and mass, then gravity/contact, rotor axes and force signs, and
only then closed-loop simulation. Sensor emulation, firmware-in-the-loop,
Gazebo integration and sim-to-real deployment are separate work. Record your
own metrics; a rendered video alone does not establish control performance.
