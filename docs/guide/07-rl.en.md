# 06 · Reinforcement learning

The previous chapter used ROS to read aircraft state, send control targets and adjust motion from sensor feedback. This chapter practices reinforcement learning in simulation, training a policy to handle wind, motor differences and model errors.

The project uses residual reinforcement learning: a geometric PD controller stabilizes attitude and allocates the four motor outputs, while a PPO network supplies acceleration corrections along three axes. For this 81 g aircraft, that keeps the explicit physical relationships in the base controller and lets the policy focus on disturbances and errors that are harder to model.

## 6.1 Turn the aircraft into a robot model

The numerical model and PPO exercises run directly from the repository. Complete aircraft URDF/USD scenes, a Gazebo flight backend and pretrained weights are not included. The reference structure and simulation videos below illustrate the modeling approach; the plots also come from simulation. If you have not prepared a separate scene, start with the CPU exercise in section 6.4 rather than running the Isaac commands.

The reference URDF/USD model uses one rigid body and four rotor joints:

[![Reference model hierarchy](/media/figures/model-hierarchy.en.svg)](/media/figures/model-hierarchy.en.svg)

`base_link` contains the parts that do not move relative to the body: printed frame, controller PCB, XIAO, rubber grommets, motor housings, power components and mounts. The IMU and optical-flow/ToF module have fixed coordinate frames for ROS and simulated sensors; their mass is already included in the rigid body. The battery retains a separate `battery_link` so its mass or position can be changed. The camera also has a fixed link, and each of the four propellers has a link on a `continuous` joint.

## 6.2 Build an initial model without a complete motor curve

The 8520 motor specifications provide dimensions and a maximum speed of 50,000 rpm, which do not directly give thrust with a 60 mm propeller. Converting the maximum speed to angular velocity gives:

```text
50,000 × 2π ÷ 60 = 5,235.99 rad/s
```

This can set a joint-speed limit, but it is not the actual loaded speed or thrust. Start with the forces on the real aircraft in hover:

```text
Mean hover thrust per motor
= total mass × gravitational acceleration ÷ 4
= 0.081 kg × 9.80665 m/s² ÷ 4
≈ 0.1986 N
≈ 20.25 gf
```

Next, read the mean of the four motor commands during stable hover from a log that includes voltage. The reference log gives about 47.4%. Extrapolating from this, the initial model uses about 0.419 N per motor at full command and a 40 ms motor response time. Training randomizes thrust gain, mass, inertia, voltage and response time so the policy does not depend too heavily on one parameter set.

These estimates are enough to begin training, evaluation and Isaac demonstrations without waiting for a complete manufacturer model. Later, build a simple single-motor thrust stand, measure several PWM points at 4.2, 3.9, 3.7 and 3.5 V, and replace the estimates with measurements.

## 6.3 Define the training task

The hover exercise has a 35-dimensional observation: position and velocity errors, attitude matrix, angular velocity, reference velocity and acceleration, previous action, integrated error, estimated motor forces and voltage. The network outputs three residual accelerations along x, y and z, bounded to `±4 m/s²`.

Each environment starts with slightly different attitude, motor parameters and wind. At each step, rewards favor:

- Staying close to the target position and velocity.
- Maintaining attitude and flight height.
- Smooth actions without frequent large corrections.
- Avoiding flips, ground impacts and leaving the flight area.

PPO runs multiple environments at once, collects observations, actions and outcomes, and uses them to update the policy. After training, compare the base PD controller and PPO residual using unseen random seeds and stronger disturbances.

## 6.4 Run your first PPO exercise on a regular computer

Create a Python environment from the repository root:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install --upgrade pip
python3 -m pip install numpy torch matplotlib
```

Run the CPU hover exercise:

```bash
python3 simulation/course/hover_lab.py \
  --output output/my-first-hover \
  --iterations 400 --envs 128 --device cpu
```

The output directory contains:

| File | Contents |
|---|---|
| `training.csv` | Reward, position error and failure count for each iteration |
| `policy_initial.pt` / `policy_final.pt` | Initial and final policies |
| `actor.pt` | A TorchScript policy that can be loaded independently |
| `evaluation.json` | PD and PPO results on held-out conditions |
| `config.json` | All training settings |

The reference run produced the following mean RMS position errors over 96 complete episodes:

| Horizontal disturbance | Base PD | PPO residual |
|---:|---:|---:|
| 0.0 m/s² | 1.58 cm | 3.64 cm |
| 0.8 m/s² | 16.51 cm | 6.03 cm |
| 1.5 m/s² | 30.48 cm | 10.56 cm |

In this run, base PD was more accurate in calm conditions. As wind disturbance increased, PPO compensation reduced position error substantially. The residual policy mainly handles persistent disturbances and model error, while the base controller remains responsible for stable flight.

## 6.6 Numerical training and optional Isaac Sim

Numerical training needs no external scene. The Isaac command at the end of this section requires compatible USD assets prepared separately, including `USD/open32droe/robot.usd` and its referenced resources. Replace the example path with your own asset directory.

The full training script uses CUDA. Run the physics checks on the training workstation first:

```bash
cd /path/to/open32drone/simulation/rl_demo
python3 physics_checks.py \
  --output ../../output/rl-demo/my-run/physics-checks.json
```

Then train, evaluate and run course preflight checks:

```bash
python3 train.py \
  --output ../../output/rl-demo/my-run \
  --iterations 1200 --envs 1024

python3 evaluate.py --run ../../output/rl-demo/my-run
python3 preflight.py --run ../../output/rl-demo/my-run
```

Use Isaac Sim's own `python.sh` to launch its separate Python environment:

```bash
/path/to/isaac-sim/python.sh \
  /path/to/open32drone/simulation/rl_demo/native_isaac.py \
  --package /path/to/open32drone/output/simulation-model/OPEN32DRON_fixed_81g \
  --run /path/to/open32drone/output/rl-demo/my-run \
  --output /path/to/open32drone/output/rl-demo/my-run/native \
  --seconds 34 --record --visible
```

`native_isaac.py` applies the combined force and torque of the four motors to the rigid body every 5 ms. PhysX integrates position and attitude. The trajectory, rings and cameras are for presentation; they do not drag the aircraft along frame by frame.

## 6.7 Work toward a real-aircraft policy

Before trying a policy on the real aircraft:

1. Replace initial maximum-thrust, response-time and reaction-torque estimates with single-motor thrust-stand measurements.
2. Add IMU, optical-flow and ToF noise, delay and dropped samples to the training environment.
3. Convert ROS-recorded state into the policy's 35-dimensional observation. Start with inference on recorded data, then proceed to constrained bench tests and low-altitude trials.

The example policy uses simulation state, and the task provides ring positions directly. A next step could add camera-based localization or target detection. Start with bounded acceleration or velocity corrections through ROS and the existing flight-control loop; consider lower-level actuator control only after collecting sufficient bench data.

These exercises cover hardware modeling, flight control, ROS and numerical training. Complete scene assets, sensor simulation and transfer to real flight still need separate preparation and validation.

## 6.8 Asset coordinates and check order

Use meters, kilograms and seconds throughout the model. The body frame is ROS FLU: X forward, Y left, Z up. Convert coordinates explicitly at firmware interfaces; do not copy CAD coordinates directly into flight parameters. Check scale, center of gravity and inertia separately. A frame model does not include all electronics, wiring, motors and battery mass, so measure the assembled aircraft.

Use simplified collision shapes without overlap. Check scale and mass first, then gravity/contact, rotor axes and force signs, and finally closed-loop simulation. Parameters in `simulation/rl_demo/model.json` are not automatically calibrated values. The adapter expects `USD/open32droe/robot.usd` relative to the asset directory. When changing scenes, check referenced meshes, materials and the Isaac version. Sensor simulation, firmware-in-the-loop, Gazebo integration and sim-to-real each require separate implementation and validation.
